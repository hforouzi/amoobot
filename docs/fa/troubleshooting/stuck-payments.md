# پرداخت‌های تاییدشدهٔ گیرکرده

پیش از اصلاح فرایند تسویهٔ پرداخت، ممکن بود پرداختی **تایید** شود ولی ساخت یا تمدید سرویس شکست بخورد. این
سفارش‌ها پرداخت شده‌اند اما انجام نشده‌اند و در فهرست «خطای ساخت سرویس» ادمین هم دیده نمی‌شوند، چون پرداختشان
تایید شده است. `PaymentSettlementService` دیگر چنین حالتی نمی‌سازد (تایید فقط همراه با انجام موفق سفارش)، اما
داده‌های قدیمی ممکن است شامل آن باشند.

## دستور

```bash
# حالت آزمایشی (پیش‌فرض): فقط فهرست، بدون هیچ تغییری
php bin/console app:payments:repair-stuck

# انتقال موارد قابل تلاش مجدد به provisioning_failed
php bin/console app:payments:repair-stuck --apply
```

گزینه‌ها:

- `--apply`: اعمال تغییرات. بدون آن چیزی تغییر نمی‌کند.
- `--include-service-missing`: سفارش‌های سرویس جدید که «ساخته‌شده» علامت خورده‌اند ولی ردیف سرویس ندارند را
  هم علامت می‌زند. ابتدا بررسی کنید؛ ممکن است ادمین سرویس را عمداً حذف کرده باشد.
- `--min-age-minutes=15`: فقط پرداخت‌هایی که حداقل این مدت پیش تایید شده‌اند.
- `--limit=200`

این دستور هیچ سرویسی نمی‌سازد یا تمدید نمی‌کند. پرداخت‌های علامت‌خورده در **ادمین > پرداخت‌ها: خطای ساخت سرویس**
نمایش داده می‌شوند و دکمهٔ **Retry provisioning** یک بار انجام سفارش را اجرا می‌کند.

## دسته‌ها

| دسته | معنی | با `--apply` |
|---|---|---|
| `new_service_not_provisioned` | تایید شده، سفارش هرگز ساخته نشده، بدون سرویس | علامت برای تلاش مجدد |
| `new_service_service_missing` | سفارش «ساخته‌شده» است ولی ردیف سرویس ندارد | فقط با `--include-service-missing` |
| `renewal_not_applied` | تمدید/افزایش حجم ثبت نشده و **پنل هنوز انقضا و حجم قبلی را نشان می‌دهد** | علامت برای تلاش مجدد (وضعیت پنل در خطا ذخیره می‌شود) |
| `renewal_maybe_applied_on_panel` | انقضای پنل دیرتر یا حجم آن بیشتر از پایگاه داده است | هرگز؛ بررسی دستی |
| `renewal_unverifiable` | پنل در دسترس نیست، سرویس هدف وجود ندارد یا مقادیر قابل مقایسه نیستند (مثل حجم نامحدود) | هرگز؛ بررسی دستی |

تمدیدها هرگز بدون مقایسهٔ وضعیت فعلی پنل برای تلاش مجدد علامت نمی‌خورند: تلاش مجدد از مقادیر پایگاه داده تمدید
می‌کند و اگر تمدید قبلاً روی پنل اعمال شده باشد، سرویس دو بار تمدید می‌شود.

## بررسی دستی تمدیدها

برای ردیف‌های `skip (manual)`:

- `renewal_maybe_applied_on_panel`: سرویس را در پنل باز کنید و با سفارش (مدت، حجم) مقایسه کنید. اگر تمدید
  اعمال شده، سرویس و سفارش را در ادمین مطابق پنل اصلاح کنید و آن را دوباره تلاش نکنید.
- `renewal_unverifiable`: پنل را در دسترس کنید (یا سرویس هدفِ گم‌شده را اصلاح کنید) و دستور را دوباره اجرا
  کنید؛ سپس `renewal_not_applied` یا `renewal_maybe_applied_on_panel` گزارش می‌شود.
